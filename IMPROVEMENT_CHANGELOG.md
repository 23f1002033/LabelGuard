# Improvement changelog

Every row records a real change and, from Milestone 2 onward, the evaluation numbers
that justified keeping or dropping it. No number in this file is written by hand; each
one comes from an `evaluation/evaluate.py` run and names the model, mode, case count
and date.

| Stage | What changed | Why | Evidence | Decision |
| --- | --- | --- | --- | --- |
| M1 setup | Rule packs for India and the UK, rule and evaluation schemas, agent interfaces, schema validator | Give both the baseline and the agent identical, sourced requirements so any later difference is attributable to the workflow and not to the rule text | `scripts/validate_schemas.py` passes: 2 rule packs, 25 rules, all sources cited with URL and excerpt | Kept |
| Baseline | OCR (tesseract) plus one Gemini 2.5 Flash call per case, given the full rule pack text and the image, returning a full requirement-by-requirement report in one shot. No retrieval step, no verification step. | Establish the naive, fair reference point the agent system has to beat, per the hackathon's required baseline-vs-agent comparison | `python evaluation/evaluate.py --system baseline` on all 7 cases (IN-001..004, UK-001..003), model gemini-2.5-flash, LABELGUARD_MODE=live, run 2026-08-31T14:02:53Z: requirement-level detection F1 = 0.8 (precision 0.75, recall 0.857, 6 tp, 2 fp, 1 fn), status accuracy 0.875, applicability accuracy 0.857, overall-status accuracy 0.714, evidence grounding rate 0.352, avg runtime 23.3s/case, 41159 tokens total. Full detail in `evaluation/results/baseline_latest.json`. | Kept as the reference baseline |
| Baseline observation 1 | none, this is an analysis finding | Both false positives came from the same case, UK-003, and both were the same failure shape: RULE-UK-FOOD-009 (country of origin) and RULE-UK-FOOD-012 (warnings) are conditionally applicable rules, and the baseline flagged them FAIL instead of NOT_APPLICABLE because it does applicability judgment and compliance judgment in a single undifferentiated call | `evaluation/results/baseline_latest.json`, case UK-003, `scores.detail` for RULE-UK-FOOD-009 and RULE-UK-FOOD-012 | Motivates a dedicated retrieval/applicability step before compliance judgment in the agent system, see docs/architecture.md section 6 |
| Baseline observation 2 | none, this is an analysis finding | RULE-IN-FOOD-011 on case IN-003 (peanuts present in ingredients but no separate Contains statement) flipped between two back-to-back live runs at temperature 0: one run correctly returned FAIL, the next returned PASS with no other input change | Two runs of `python evaluation/evaluate.py --system baseline --cases IN-003` on 2026-08-31, same model and temperature | Motivates a verification step that re-checks candidate findings against extracted evidence rather than trusting a single pass, see docs/architecture.md section 6; this is the specific instability the M4 iteration should try to reduce |
| Agent v1 | Built the four-agent pipeline: extraction agent (OCR + vision LLM call producing structured, per-field confidence and evidence facts), retrieval agent (deterministic, non-LLM applicability engine matching rule conditions against derived signals), compliance agent (LLM call over structured facts and only the rules retrieval marked applicable), verification agent (LLM call that only challenges candidate FAIL findings, can downgrade to NEEDS_REVIEW/PASS, can never upgrade to FAIL) | Directly address Baseline observations 1 and 2: separate applicability from compliance judgment, and add a check on FAIL claims before they reach the report | First live run on all 7 cases, 2026-08-31T14:38Z: F1 dropped to 0.833 (2 false negatives, IN-003 and UK-003) even though applicability accuracy hit 1.0 (both baseline false positives eliminated) | Applicability fix kept; false negatives investigated below before accepting v1 |
| Agent v1 bug 1 | Investigated the IN-003 false negative (missed the allergen-Contains violation entirely) | `extraction_agent._to_extracted_field` was hard-capping confidence at 0.3 for every `present=False` field regardless of the model's actual certainty. The raw model output for the missing allergen statement was `confidence=1.0` (fully certain it is absent); the artificial cap made a confidently-absent fact look like a shaky extraction, and the compliance agent reasonably treated that as grounds for NEEDS_REVIEW instead of FAIL | Verified the raw pre-clamp API response directly showed confidence 1.0; removed the clamp | Fixed; this directly contradicted the project's own evidence-first principle (confident absence is exactly the kind of grounded claim the report should be able to make), see docs/decisions.md M3-01 |
| Agent v1 bug 2 | Investigated why several genuinely-compliant requirements (FSSAI licence, net quantity block, date grouping, ingredients ordering) were coming back NEEDS_REVIEW instead of PASS across multiple cases | The compliance agent receives the full legal `requirement` text, which often names sub-details (colour contrast, spatial grouping, true manufacturing weight order) that this MVP does not extract as separate facts. The model was correctly declining to confidently PASS something it had no evidence for, which is honest but too strict given what the rule pack already documents as out of scope | Added `notes` fields to 6 rules (RULE-IN-FOOD-002/006/009, RULE-UK-FOOD-002/005/006) stating the actual MVP-checked scope, and wired `rule.notes` into the compliance prompt so the model judges against the documented scope instead of the full legal text | Fixed; considered and rejected instructing the model to "PASS anyway despite missing evidence", which would have been an unsupported claim, see docs/decisions.md M3-02 |
| Agent v1 bug 3 | Investigated the UK-003 false negative (missed the missing-FBO-address violation) | The extraction agent's field description for `business_name_address` said "the name and address" but did not explicitly rule out a bare brand name; the vision model accepted the decorative front-panel brand name "RIVERSIDE MILLS" as satisfying the field even though no physical address appears anywhere on the pack, which is exactly the trap this case was built to test | Sharpened the field description to require a physical address component and explicitly state a brand name alone does not count | Fixed; verified directly against the case before re-running the full batch |
| Agent v2 | All three v1 bugs fixed, same 4-agent architecture, same 7 cases | Confirm the fixes actually work together, not just in isolation | Two consecutive full live runs, 2026-08-31T14:56Z and T15:00Z, model gemini-2.5-flash: F1 = 1.0 both times (7 tp, 0 fp, 0 fn), applicability accuracy 1.0, overall-status accuracy 1.0, status accuracy 0.955 and 0.966, evidence grounding rate 0.44-0.48, avg runtime 33-35s/case (up from baseline's 23.3s), 72k-74k tokens/run (up from baseline's 41k). Full detail in `evaluation/results/agent_latest.json`. | Kept as the Milestone 3 agent system. Baseline vs agent: F1 0.8 to 1.0, applicability accuracy 0.857 to 1.0, overall-status accuracy 0.714 to 1.0, evidence grounding 0.352 to ~0.46, at roughly 1.5x the runtime and 1.8x the tokens of the baseline |
