# Improvement changelog

Every row records a real change and, from Milestone 2 onward, the evaluation numbers
that justified keeping or dropping it. No number in this file is written by hand; each
one comes from an `evaluation/evaluate.py` run and names the model, mode, case count
and date.

| Stage | What changed | Why | Evidence | Decision |
| --- | --- | --- | --- | --- |
| M1 setup | Rule packs for India and the UK, rule and evaluation schemas, agent interfaces, schema validator | Give both the baseline and the agent identical, sourced requirements so any later difference is attributable to the workflow and not to the rule text | `scripts/validate_schemas.py` passes: 2 rule packs, 25 rules, all sources cited with URL and excerpt | Kept |
| Baseline | OCR (tesseract) plus one Gemini 2.5 Flash call per case, given the full rule pack text and the image, returning a full requirement-by-requirement report in one shot. No retrieval step, no verification step. | Establish the naive, fair reference point the agent system has to beat, per the hackathon's required baseline-vs-agent comparison | `python evaluation/evaluate.py --system baseline` on all 7 cases (IN-001..004, UK-001..003), model gemini-2.5-flash, LABELGUARD_MODE=live, run 2026-08-31T14:02:53Z: requirement-level detection F1 = 0.8 (precision 0.75, recall 0.857, 6 tp, 2 fp, 1 fn), status accuracy 0.875, applicability accuracy 0.857, overall-status accuracy 0.714, evidence grounding rate 0.352, avg runtime 23.3s/case, 41159 tokens total. Full detail in `evaluation/results/baseline_latest.json`. | Kept as the reference baseline |
| Baseline observation 1 | none, this is an analysis finding | Both false positives came from the same case, UK-003, and both were the same failure shape: RULE-UK-FOOD-009 (country of origin) and RULE-UK-FOOD-012 (warnings) are conditionally applicable rules, and the baseline flagged them FAIL instead of NOT_APPLICABLE because it does applicability judgment and compliance judgment in a single undifferentiated call | `evaluation/results/baseline_latest.json`, case UK-003, `scores.detail` for RULE-UK-FOOD-009 and RULE-UK-FOOD-012 | Motivates a dedicated retrieval/applicability step before compliance judgment in the agent system, see docs/architecture.md section 6 |
| Baseline observation 2 | none, this is an analysis finding | RULE-IN-FOOD-011 on case IN-003 (peanuts present in ingredients but no separate Contains statement) flipped between two back-to-back live runs at temperature 0: one run correctly returned FAIL, the next returned PASS with no other input change | Two runs of `python evaluation/evaluate.py --system baseline --cases IN-003` on 2026-08-31, same model and temperature | Motivates a verification step that re-checks candidate findings against extracted evidence rather than trusting a single pass, see docs/architecture.md section 6; this is the specific instability the M4 iteration should try to reduce |
