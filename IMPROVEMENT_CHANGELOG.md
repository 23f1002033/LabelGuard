# Improvement changelog

Every row records a real change and, from Milestone 2 onward, the evaluation numbers
that justified keeping or dropping it. No number in this file is written by hand; each
one comes from an `evaluation/evaluate.py` run and names the model, mode, case count
and date.

| Agent v1 | Built the four-agent pipeline: extraction agent (OCR + vision LLM call producing structured, per-field confidence and evidence facts), retrieval agent (deterministic, non-LLM applicability engine matching rule conditions against derived signals), compliance agent (LLM call over structured facts and only the rules retrieval marked applicable), verification agent (LLM call that only challenges candidate FAIL findings, can downgrade to NEEDS_REVIEW/PASS, can never upgrade to FAIL) | Directly address Baseline observations 1 and 2: separate applicability from compliance judgment, and add a check on FAIL claims before they reach the report | First live run on all 7 cases, 2026-08-31T14:38Z: F1 dropped to 0.833 (2 false negatives, IN-003 and UK-003) even though applicability accuracy hit 1.0 (both baseline false positives eliminated) | Applicability fix kept; false negatives investigated below before accepting v1 |
| Agent v1 bug 1 | Investigated the IN-003 false negative (missed the allergen-Contains violation entirely) | `extraction_agent._to_extracted_field` was hard-capping confidence at 0.3 for every `present=False` field regardless of the model's actual certainty. | Agent v1 bug 2 | Investigated why several genuinely-compliant requirements (FSSAI licence, net quantity block, date grouping, ingredients ordering) were coming back NEEDS_REVIEW instead of PASS across multiple cases | The compliance agent receives the full legal `requirement` text, which often names sub-details (colour contrast, spatial grouping, true manufacturing weight order) that this MVP does not extract as separate facts.
